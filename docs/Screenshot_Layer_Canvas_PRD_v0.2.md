## 1. 제품 한 줄 정의

웹·앱 화면 캡처를 업로드하고, 화면 일부를 이미지 레이어로 추출해 캔버스에서 재배치한 뒤 PNG로 저장하는 브라우저 기반 목업 편집기.

## 2. 판정

**좁힌 범위(Phase 1)로 바로 프로토타입 제작 가능.**

스크린샷을 HTML 컴포넌트로 복원하는 서비스로 정의하면 실패 확률이 높다. 초기 제품은 다음으로 제한한다.

> 화면의 보이는 요소를 선택 가능한 이미지 조각으로 만들고 빠르게 재배치하는 목업 편집기.

초기 성공 기준은 코드 품질이 아니라 **재배치 시안을 만드는 시간이 줄어드는가**이다.

## 3. 해결하려는 문제

기존 화면의 배치를 바꾼 시안을 만들려면 보통 캡처 → 포토샵에서 요소 잘라내기 → 빈자리 정리 → 재배치 순서로 작업한다. 이 제품은 이 과정을 한 화면에서 처리한다.

## 4. 주요 사용자

- 원본 Figma 파일 없이 기존 화면을 개선해야 하는 기획자
- 캡처로 빠르게 수정 시안을 만드는 디자이너
- 레퍼런스 화면을 재구성해 개발 지시를 만드는 1인 개발자

## 6. M3E Canvas 참고 방침

참고 저장소: https://github.com/lnkiai/m3e-canvas

- 포크하지 않고 **새 프로젝트로 제작**하는 방향을 우선 검토한다. M3E는 UI 컴포넌트 노드 중심이고, 이 제품은 원본 이미지·크롭 좌표·비트맵 레이어 중심이다.
- 캔버스 이동·확대, 선택, Undo/Redo UX와 단축키만 참고한다.
- 최종 선택(포크/신규)은 Claude Code가 저장소를 분석한 뒤 근거와 함께 제안한다.

## 7. 핵심 사용자 흐름 (Phase 1)

1. 새 프로젝트 생성
2. 캡처 업로드 → 원본 크기 프레임 표시
3. 사각형 영역 선택 → 레이어로 추출
4. 레이어를 이동·복제·삭제하고 순서 조정
5. 원래 자리가 대표 배경색으로 채워짐 (색상 수정 가능)
6. PNG 출력, 프로젝트 JSON 저장
7. 프로젝트 JSON을 다시 열어 위치·순서 복원 확인

## 8. 화면 구조 (Phase 1)

- **상단 바**: 프로젝트명, 이미지 업로드, Undo/Redo, 저장, PNG 내보내기
- **왼쪽 도구**: 선택, 손(이동), 영역 추출, 배경 채움
- **중앙 캔버스**: 확대·축소·이동 가능한 작업 공간, 화면 프레임
- **오른쪽 패널**: 선택 레이어의 이름·X·Y·너비·높이(읽기 전용), 앞/뒤 순서, 레이어 목록

화면 라벨과 PNG 출력 크기는 **업로드한 원본 이미지의 너비 × 높이**를 따른다. 와이어프레임의 1440×900은 예시값이다.

## 9. 빈자리 처리

생성형 복원은 사용하지 않는다.

1. 선택 영역 **바깥** 1~5px 테두리에서 색상 샘플링 (평균보다 중앙값 또는 최빈색 우선)
2. 선택 영역이 있던 자리를 대표색으로 채움
3. 샘플 편차가 임계값보다 크면 자동 채우기를 중단하고 사용자에게 색상 선택을 요청
4. 사용자가 색상 피커로 직접 수정 가능

## 10. 기능 요구사항

### FR-01 이미지 업로드
- PNG/JPG를 업로드할 수 있다.
- 원본 픽셀 크기로 화면 프레임을 만들고, 원본 파일은 수정하지 않고 보존한다.

### FR-02 영역 추출
- 사용자가 지정한 사각형을 알파 채널이 있는 이미지 레이어로 추출한다.
- 추출은 원본 픽셀 좌표 기준이며 뷰포트 확대·축소와 무관하다.
- 추출 전후를 취소·복구할 수 있다.

### FR-03 레이어 조작
- 선택·이동·복제·삭제·앞뒤 순서 변경이 가능하다.
- 순서 변경은 즉시 캔버스에 반영된다.

### FR-04 배경 정리
- 추출 후 남은 자리를 감지한 대표색으로 채운다.
- 사용자가 색상을 다시 선택할 수 있고, 되돌릴 수 있다.

### FR-05 저장 및 출력
- 현재 화면을 원본 크기 PNG로 저장한다. 투명 영역은 실제 알파 채널이며 확인용 체크무늬는 절대 포함하지 않는다.
- 전체 편집 상태를 프로젝트 JSON(및 Blob)으로 저장하고 다시 불러올 수 있다.
- 임시 Blob URL만 기록하는 방식은 금지한다.

## 11. 프로젝트 데이터 구조

**처음부터 `screens[]` 구조를 쓴다.** Phase 1에서는 `screens`에 화면 하나만 허용하고, Phase 2 다중 화면은 구조 변경 없이 확장한다.

```ts
type Project = {
  id: string;
  name: string;
  version: 1;
  canvas: { zoom: number; panX: number; panY: number };
  screens: ScreenNode[];            // Phase 1: 길이 1만 허용
};

type ScreenNode = {
  id: string;
  name: string;
  x: number;                        // 캔버스상 위치 (Phase 1은 0,0)
  y: number;
  width: number;                    // 원본 이미지 너비 (px)
  height: number;                   // 원본 이미지 높이 (px)
  source: {
    imageId: string;                // Blob 참조 (IndexedDB / 프로젝트 파일)
    fileName: string;
  };
  backgroundPatches: BackgroundPatch[];
  layers: BitmapLayer[];
};

type BitmapLayer = {
  id: string;
  name: string;
  crop: { x: number; y: number; width: number; height: number };  // 원본 픽셀 좌표
  imageId?: string;                 // 추출 비트맵 Blob 참조 (필요 시)
  transform: {
    x: number;                      // 화면 프레임 기준 원본 픽셀 좌표
    y: number;
    scaleX: 1;                      // Phase 1 고정값 (1.5에서 활성화)
    scaleY: 1;
    rotation: 0;                    // Phase 1 고정값 (1.5에서 활성화)
  };
  zIndex: number;
  opacity: number;                  // Phase 1은 1
  visible: boolean;                 // Phase 1은 true
  locked: boolean;                  // Phase 1은 false
};

type BackgroundPatch = {
  id: string;
  rect: { x: number; y: number; width: number; height: number };
  fill: string;
};
```

선택 상태(`selectedLayerIds`)는 UI 상태이며 프로젝트 파일에 저장하지 않아도 된다.

## 12. 권장 기술 구성

- Next.js App Router + React + TypeScript + Tailwind CSS
- 캔버스: Konva.js 우선 검토
- 상태 관리: Zustand 또는 reducer 기반 히스토리 (이미지 픽셀 복사 없이 명령/상태 차이만 기록)
- 로컬 저장: IndexedDB
- 이미지 처리: Canvas API (외부 AI·유료 API 없음)
- 테스트: Vitest + Playwright

## 13. 성능 요구사항

- 1920×1080 이미지 기준 업로드 후 2초 이내 편집 가능
- 드래그 중 30fps 이상
- Undo 히스토리 50단계 이상
- 원본 해상도 PNG 출력 시 위치 오차 1px 이내

## 14. 수용 기준 (Phase 1)

아래가 모두 성공하면 Phase 1 완료로 본다.

1. 웹앱 캡처 이미지를 업로드하면 원본 크기 프레임이 표시된다.
2. 카드 또는 버튼 하나를 사각형으로 추출해 레이어를 만든다.
3. 추출 레이어 크기가 선택 영역 크기와 일치한다.
4. 레이어를 다른 위치로 이동한다.
5. 원래 위치가 대표 배경색으로 채워진다.
6. 200% 확대 상태에서 추출해도 원본 픽셀 기준 위치가 틀어지지 않는다.
7. 결과 PNG 크기가 업로드한 원본 크기와 정확히 일치한다.
8. 프로젝트를 저장하고 다시 열면 레이어 위치와 순서가 유지된다.
9. 자동 분해처럼 보이기만 하는 가짜 기능이 없다.

## 15. 실패 가능성이 높은 지점

- **자동 분해 과대평가**: 카드 안에 글자·아이콘·이미지가 중첩되어 있어 자동 결과가 사용자의 "하나의 요소"와 일치하지 않는다. Phase 1은 수동 추출만 한다.
- **텍스트 편집 동시 도입**: OCR·글꼴·자간 복원은 별도 난이도다. 글자는 이미지 조각으로만 다룬다.
- **M3E 포크**: 컴포넌트 중심 데이터 모델과 비트맵 레이어 모델이 충돌할 수 있다. 신규 제작을 우선 검토한다.
- **좌표계 혼용**: 화면 표시 좌표와 원본 픽셀 좌표를 섞으면 확대 시 위치가 틀어진다.

## 16. 검증 계획

1. 서로 다른 웹앱 캡처 10장으로 직접 분리한 시안을 만들어 사용자가 바꾸고 싶어 하는 요소 유형을 기록
2. 수동 추출 프로토타입(Phase 1)으로 한 화면 재배치 시간을 측정하고 포토샵과 비교
3. 사용 빈도가 높은 요소부터 자동 후보 제안(Phase 3) 검토

핵심 지표: 첫 레이어 추출 완료 시간, 화면 하나 재배치 완료 시간, 화면당 Undo 횟수, PNG 출력까지 완료한 비율.

## 17. 최종 MVP 정의

> 사용자가 스크린샷을 업로드하고, 원하는 사각형 영역을 이미지 레이어로 뽑아 재배치한 뒤, 새 화면 목업을 원본 크기 PNG로 저장할 수 있다.

가장 중요한 것은 **선택 → 분리 → 이동 → 빈자리 정리 → 출력**이 끊기지 않고 실제로 동작하는 것이다.
