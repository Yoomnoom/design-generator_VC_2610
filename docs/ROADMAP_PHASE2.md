# Phase 2 로드맵과 결정

MVP는 확정되었고(태그 `mvp`), Phase 2는 재배치 중에 외부 편집기로 나가지 않도록 그리기·주석·자동 후보를 더하는 단계다. 기존 `docs/`의 PRD·핸드오프·와이어프레임은 Phase 1 기준이라 수정하지 않는다. 범위와 규칙의 기준은 루트 `CLAUDE.md`와 이 문서다.

## 하지 않는 것

외부 AI·유료 API, 서버 저장·계정, 다중 화면, 포토샵식 필터·색 보정·클론 스탬프·마술봉.

## 순서와 상태

| # | 기능 | 상태 |
|---|---|---|
| 1 | 선·도형(사각형·원)·스포이트, 벡터 레이어(스키마 v3) | 완료 |
| 2 | 브러시·지우개(스키마 v4) | 완료 |
| 3 | 텍스트 상자(스키마 v5) | 완료 |
| 4 | 메모(스키마 v6) | 완료 |
| 5 | 자동 영역 후보(Web Worker, 고전적 이미지 처리) | 완료 |
| 6 | 키보드 레이어 이동 | 완료 |
| 7 | 다중 선택·그룹 이동, 정렬 가이드·스냅(8px 간격 포함) | 완료 |

(이 표는 기능이 끝날 때마다 갱신한다. 막혀서 건너뛴 것은 아래 "막힌 것"에 원인과 함께 적는다.)

## 공통 규칙

- 각 기능은 타입 검사, 단위 테스트, 관련 E2E가 통과해야 완료이고, 변이 검사를 포함한다. 완료할 때마다 커밋하고 origin에 push한다(force push 없음).
- 스키마를 바꾸면 `version`을 올리고 `migrate.ts`에 단계를 더하며, 이전 버전이 *실제로 저장한* 파일을 `tests/fixtures/`에 둔다(`project-v1`, `project-v2`).
- 좌표는 원본 픽셀 기준이고 200% 확대·DPR 2에서 화면과 PNG가 일치해야 한다. PNG 크기는 항상 원본 크기다.
- Undo/Redo에 이미지 픽셀을 복사하지 않는다(상태 차이와 `imageId` 참조만).
- 새 기능은 임시저장 복원, 프로젝트 저장·불러오기, 비교 보기 중 편집 차단, 잠금·숨김과 함께 동작하는지 각각 테스트한다.
- E2E는 브라우저를 한 번에 하나만 띄운다(`playwright.config.ts`의 `workers: 1`).

## 1. 선·도형·스포이트 (결정)

- **벡터 레이어**는 `BitmapLayer`에 선택 필드 `content`(`line`/`rect`/`ellipse`)를 둔 것이다. `content`가 있으면 `imageId`가 없고 `crop`은 빈 사각형이다. 새 레이어 타입을 따로 만들지 않은 이유는 선택·이동·복제·삭제·순서·잠금·숨김·이름·회전·Undo·저장 경로를 그대로 쓰기 위해서다.
- **크기 조절은 배율이 아니라 상자(width/height)에 굽는다.** 벡터 레이어의 `scaleX/scaleY`는 항상 1이고 선 굵기는 그대로다. 회전은 상자의 왼쪽 위 모서리 기준이다.
- **선**은 상자의 한 대각선이다(`direction`: `down`은 왼쪽 위→오른쪽 아래, `up`은 왼쪽 아래→오른쪽 위). 가로·세로 선도 높이·너비 1의 상자를 가져서 선택·조절이 된다. 굵기는 1 이상.
- **그리기 함수는 하나**(`drawContent`): 화면(Konva `Shape`의 `sceneFunc`)과 PNG(OffscreenCanvas)가 같은 함수로 그린다. PNG는 레이어를 프레임 좌표로 그려 정수 위치의 비트맵으로 합성하므로 다시 샘플링하지 않는다. 가장자리는 캔버스의 안티앨리어싱이다. 프로젝트 파일에는 설명만 저장하고 픽셀은 저장하지 않는다.
- **색·굵기 변경**은 속성 패널에서 한다. 색 선택기는 끄는 동안(`input`)은 견본만 바꾸고 확정(`change`)에 1단계, 굵기는 Enter·포커스 이동에 1단계이며 Escape는 취소다. 테두리와 채움이 모두 없는 도형은 만들 수 없다.
- **그리기 설정**(테두리색, 채움색/없음, 굵기, 스포이트 대상)은 프로젝트 데이터가 아니라 UI 상태다.
- **스포이트**는 화면 캔버스가 아니라 *합성 결과*(원본+패치+레이어, `renderProjectRaw`)에서 픽셀을 읽는다. zoom·DPR과 무관하고 숨긴 레이어는 보이지 않는다. 투명한 픽셀은 거부하고 알린다. 읽은 색은 `pickTarget`(테두리 또는 채움)에 들어간다.
- **단축키**: L(선), M(사각형), O(원), I(스포이트). 기존 V·H·R·Ctrl 조합과 겹치지 않는다.
- **측정**(Chromium 헤드리스, 100% 확대): 화면 대 PNG 픽셀 차이는 DPR 1에서 최대 채널 차이 1(샘플 100곳), DPR 2에서는 가장자리 2곳이 최대 78(캔버스 해상도가 2배라 가장자리 안티앨리어싱 픽셀이 다르다). 4000×3000 이미지에 큰 사각형이 있을 때 스포이트 클릭은 173ms(전체 합성 포함), PNG 내보내기는 342ms.

## 2. 브러시·지우개 (결정)

- **비트맵 갱신 방식(요청 보고 항목)**: 이미지는 불변이다. 한 획이 끝나면 캔버스로 *새 비트맵*을 만들어 새 `imageId`로 캐시에 넣고, 레이어의 `imageId`·`crop`·`transform.x/y`만 바꾼다(`commitBitmapEdit`). 히스토리에는 이 몇 개 값의 차이만 쌓이고(패치 700바이트 미만, 픽셀 없음) 이전 비트맵은 Undo를 위해 캐시에 남는다. 프로젝트 파일·임시저장에는 레이어의 *현재* 비트맵만 저장된다.
- **브러시 레이어**는 `drawn: true`인 비트맵 레이어다(스키마 v4, 선택 필드). 브러시는 선택된 브러시 레이어가 보이고 잠기지 않았고 크기·회전이 없을 때만 그 레이어에 이어 그리고(비트맵은 프레임 안에서 자란다), 아니면 새 "브러시 N" 레이어를 만든다.
- **지우개는 선택된 브러시 레이어에만** 쓴다. 원본 이미지, 추출한 레이어, 도형에는 거부하고 이유를 안내 줄에 보여 준다(잠김, 숨김, 크기·회전 변경도 각각 이유를 말한다). 비트맵 크기는 바뀌지 않고, 닿는 것이 없으면 기록하지 않는다. **원본 이미지는 어떤 경우에도 수정하지 않는다**(테스트가 메모리의 픽셀 해시로 확인).
- **한 획 = Undo 1단계.** 드래그 중에는 미리보기만 그리고 비트맵은 놓을 때 한 번 칠한다. 색은 그리기 설정의 색(스포이트 대상 "테두리"), 크기는 1~200.
- **단축키**: B(브러시), E(지우개).
- **측정**(4000×3000, 헤드리스): 화면 대부분을 가로지르는 첫 획(상자 3262×2262) 393ms(드래그 포함), 두 번째 획 248ms, 지우개 212ms. Undo용으로 남는 비트맵은 이미지 4개에 130MB다(획마다 새 비트맵을 남기므로 획이 많으면 메모리가 늘고, 오래된 비트맵을 정리하는 것은 아직 하지 않았다).

## 3. 텍스트 상자 (결정)

- **텍스트 레이어**는 벡터 레이어의 한 종류다(`content.kind: "text"`, 스키마 v5, 4→5 마이그레이션은 변경 없음). 내용은 `text`, `fontSize`(4~400), `color`(#rrggbb), `align`(left/center/right), `width`, `height`이며 테두리·채움은 없다(`stroke: null`, `strokeWidth: 0`). 빈 글자·공백뿐인 글자는 파일 검증에서도 거부한다(보이지 않는 레이어를 막기 위해).
- **같은 함수로 그린다**: 화면(Konva `Shape`)과 PNG(OffscreenCanvas)가 모두 `drawContent` → `drawText`를 부른다. 줄바꿈은 `text-layout.ts`(`wrapText`/`layoutText`, 줄 높이 = 글자 크기 × 1.3)이 정하고, 폭은 **그리는 컨텍스트의 `measureText`**로 잰다. 그래서 화면과 PNG의 줄바꿈이 같은 자리에서 일어난다. 공백에서 먼저 줄을 바꾸고, 상자보다 넓은 한 단어(긴 주소, 공백 없는 한글)는 글자 사이에서 끊는다.
- **높이는 줄이 정한다**: `height`는 줄바꿈 결과(`fitHeight`)로 편집기가 맞춰 저장한다(글자·크기·너비가 바뀔 때마다). 글자 폭을 재는 방법은 스토어 옵션(`measure`)이며 브라우저에서는 캔버스, Node(단위 테스트)에서는 고정 추정식(`estimateMeasure`: 한글·한자·이모지 1.0 × 글자 크기, 그 밖 0.55)이다. 추정식은 테스트용이며 실제 폭과 다르다는 점을 숨기지 않는다.
- **글꼴**: `"Noto Sans KR", "Malgun Gothic", "Apple SD Gothic Neo", system-ui, sans-serif`. 웹폰트를 내려받지 않으므로 사용자 컴퓨터에 있는 글꼴이 쓰이고, 같은 컴퓨터의 화면과 PNG는 같다. **다른 컴퓨터에서 같은 프로젝트를 열면 글꼴이 달라 줄바꿈이 달라질 수 있다**(프로젝트는 글꼴 파일을 담지 않는다).
- **만들기**: 텍스트 도구(T)로 캔버스를 클릭 → 그 자리에 입력창이 열리고(`TextEditor`, 캔버스 확대율·상자 각도에 맞춰 같은 자리에 겹침) 글자를 입력한다. **입력창을 벗어나거나 Ctrl+Enter면 확정**(레이어 생성 = Undo 1단계), **Esc는 취소**. 글자가 비어 있으면 아무것도 만들지 않는다. 입력창이 열린 채 캔버스의 다른 곳을 클릭하면 확정만 하고 새 상자는 열지 않는다(다음 클릭이 다음 상자). 열자마자(250ms 이내) 생기는 포커스 이탈은 열게 한 클릭이 포커스를 되가져간 것으로 보고 무시한다.
- **고치기**: 선택 도구로 텍스트 상자를 **두 번 클릭**하면 같은 입력창이 열린다. 비우고 나가면 이전 글자를 유지한다. 잠긴 레이어와 비교 보기에서는 열리지 않는다(스토어가 거부). 속성 패널에서도 글자(나갈 때 확정, Esc 취소)·크기·색·정렬을 바꾼다 — 각각 Undo 1단계. 새 상자의 기본값(크기 32, 색 #222222, 왼쪽 정렬)은 텍스트 도구를 켜면 나오는 패널에서 정한다.
- **크기 조절·회전**: 옆 핸들(왼쪽·오른쪽 가운데)은 **상자 너비**만 바꾸고 높이는 줄바꿈이 정한다(글자 크기는 그대로, `scale`은 1 고정). 모서리·위아래 핸들은 텍스트 상자에는 없다. 회전은 다른 레이어와 같이 위쪽 둥근 핸들.
- **OCR 없음**: 이미지 속 글자를 읽어 텍스트로 바꾸는 기능은 없다. 텍스트 상자는 사용자가 직접 입력한 글자다.
- **측정(화면 대 PNG의 글자 위치 차이)**: 각 이미지 픽셀의 "잉크량"(페이지 회색과의 거리)을 캔버스(그 픽셀을 덮는 화면 픽셀의 평균)와 PNG에서 읽어 비교했다. 무게중심 차이는 **모든 조합에서 0.4px 이하**, 글자가 차지하는 영역(잉크 > 25%)의 경계 차이는 **0px**, 잉크 총량 비는 0.999~1.021. 100%·200% 확대, devicePixelRatio 1·2, 회전 0°·15°를 모두 쟀다(회전한 쪽이 더 작다).

  | DPR | 확대 | 회전 | 무게중심 dx / dy (px) | 경계 차이 | 잉크 비 |
  |---|---|---|---|---|---|
  | 1 | 100% | 0° | -0.005 / -0.017 | 0 | 1.000 |
  | 1 | 100% | 15° | -0.002 / -0.004 | 0 | 1.000 |
  | 1 | 200% | 0° | 0.375 / -0.154 | 0 | 1.021 |
  | 1 | 200% | 15° | -0.016 / -0.016 | 0 | 1.008 |
  | 2 | 200% | 0° | 0.234 / -0.113 | 0 | 1.021 |
  | 2 | 200% | 15° | -0.001 / -0.021 | 0 | 1.012 |

  (확대 200%에서 약간 큰 차이는 화면이 글자를 더 큰 격자에 그리므로 안티앨리어싱의 모양이 달라서다. 글자의 위치가 어긋난 것이 아니다.) 헤드리스 Chromium 한 대에서만 쟀다.
- **측정(큰 캡처)**: 4000×3000에서 상자 20개 추가 15ms(개당 0.8ms), 한 상자 수정 2.1ms, 20개 포함 PNG 내보내기 725ms. 8000×6000에서 추가 17ms, 수정 25ms, 내보내기 814ms. 헤드리스, 한 번씩 쟀다.
- **알려진 한계**: 굵게·기울임·밑줄·글꼴 선택·줄 간격·글자 간격·그림자는 없다. 한 상자는 글자 한 가지 모양이다. 입력 중 미리보기는 브라우저 텍스트 영역의 줄바꿈이고, 확정되면 위의 규칙으로 다시 줄바꿈된다(드물게 한 줄의 끊는 자리가 달라 보일 수 있다). 입력 방식(IME)으로 한글을 조합하는 도중 포커스를 잃는 경우의 동작은 확인하지 못했다(자동화로 재현하지 못함).

## 4. 메모 (결정)

- **메모는 레이어가 아니다.** 화면(`ScreenNode.memos`: `{id, x, y, text}` 목록, 스키마 v6, 5→6 마이그레이션은 변경 없음)에 붙는 편집용 표시다. 레이어 목록·z순서·잠금·숨김·복제·붙여넣기와 무관하고, 레이어가 잠기거나 숨겨져 있어도 메모는 만들고 고칠 수 있다(테스트로 확인). 좌표는 원본 픽셀이며 프레임 안(0~너비/높이)으로 제한한다(스토어가 맞추고 파일 검증도 거부한다). 한 화면에 최대 200개, 글자는 1000자까지(빈 글자 허용: 핀만 남는다). 번호는 목록 순서(만든 순서)이다.
- **PNG에는 기본으로 들어가지 않는다.** 내보내기 대화상자에 "메모 포함" 선택이 있다(기본 꺼짐, 메모가 없으면 비활성). 꺼져 있으면 메모가 있어도 PNG는 메모가 없는 같은 화면의 PNG와 **바이트까지 같다**(E2E로 확인). 켜면 번호가 붙은 빨간 핀(반지름 12px)과, 글자가 있으면 오른쪽의 말풍선(최대 폭 220px, 14px 글자, 프레임 안으로 밀어 넣음)이 그려진다. 크기는 이미지 픽셀 기준이라 확대율과 무관하다. 투명한 캡처는 메모 둘레도 투명 그대로 남는다(알파 합성). PNG 크기는 항상 원본 크기다.
- **그리는 방식**: 메모마다 작은 OffscreenCanvas에 그려 `compositeOver`(straight-alpha source-over)로 합성한다. 큰 캡처 전체를 복사하지 않는다. 핀·말풍선의 배치는 `layoutMemo`(순수 기하), 그리기는 `drawMemo`가 맡는다. 겹치는 메모를 피해 배치하지는 않는다(뒤 번호가 위에 그려진다).
- **편집기에서**: 핀(24px 번호 원)과 선택된 메모의 말풍선은 캔버스 위의 HTML이다(`MemoLayer`). 확대율과 무관하게 같은 크기이고, 이미지 점에 붙어 확대·이동을 따라간다. 메모 도구(N)로 캔버스를 클릭하면 그 픽셀에 빈 메모가 생기고(Undo 1단계) 말풍선이 열려 바로 입력한다. 글자는 입력창을 벗어날 때 확정된다(Undo 1단계, Esc는 되돌림). 핀을 끌면 이동(화면 거리 ÷ 확대율 = 이미지 픽셀, 3px 미만은 클릭, 놓을 때 Undo 1단계). 삭제는 말풍선의 버튼, Delete 키(레이어 선택이 없고 입력창이 아닐 때), Undo. 우측 패널의 "메모" 목록으로도 고른다. 선택하지 않은 핀은 마우스를 올리면 글자가 툴팁으로 보인다(말풍선은 선택된 것만).
- **비교 보기**(원본/나란히)에서는 핀을 그리지 않고, 메모 도구·목록·스토어의 모든 메모 동작이 거부된다. 원본에는 메모가 없기 때문이다.
- **임시저장·프로젝트 저장**: 메모는 프로젝트의 일부라서 둘 다 자동으로 포함되고, 위치·글자·순서가 복원된다(E2E). 버전 5 파일(메모 없음)은 그대로 열린다(`tests/fixtures/project-v5.slc.json`).
- **측정**(헤드리스, 한 번씩): 4000×3000에서 메모 100개 추가+글자 23ms, 한 번 Undo 0.5ms, 메모 100개 포함 PNG 내보내기 343ms(메모 없이 410ms: 첫 내보내기의 준비 시간이 섞인 값이라 차이는 의미가 없다). 8000×6000에서 30ms, 0.7ms, 728ms(메모 없이 853ms).
- **알려진 한계**: 메모에 색·작성자·시간·답글·"해결됨" 같은 것은 없다. 말풍선 위치는 핀 오른쪽 고정이다(편집기에서 직접 옮길 수 없고 핀만 옮긴다). 편집기 말풍선은 열려 있는 동안 아래 캔버스 클릭을 가린다. 내보낸 말풍선의 줄바꿈은 위 규칙의 고정 폭이며 편집기 입력창의 줄바꿈과 다를 수 있다. 한글 IME 조합 중 포커스 이탈은 확인하지 못했다.

## 5. 자동 영역 후보 (결정)

- **AI도 외부 API도 아니다.** 고전적 이미지 처리만 쓴다(`src/lib/image/candidates.ts`). 이웃한 두 픽셀의 색 차이(R·G·B·A 중 가장 큰 채널)가 **허용치 4 이하**면 같은 덩어리로 묶고(가로로 같은 색인 구간을 먼저 묶어 union-find), 덩어리마다 바깥 상자를 후보로 삼는다. 흰 카드는 구멍(글자·버튼)이 있는 한 덩어리이고, 구멍들이 각각 후보라서 카드 안의 버튼도 찾는다. 그림자·그라데이션은 천천히 변해 배경에 붙으므로 카드에 섞이지 않는다. 버려지는 것: 한 변이 8px 미만(글자 한 획 같은 잡음), 프레임의 90% 초과(페이지 전체), 자기 상자를 15% 미만으로 채우는 것(얇은 테두리·흩어진 점). 결과는 같은 입력에 항상 같다.
- **Web Worker에서 돈다**(`candidates.worker.ts`, `analyser.ts`). 편집기의 원본 픽셀은 복사해서 보내므로 편집기는 그대로 쓸 수 있다. 새 요청은 아직 안 끝난 이전 요청을 "superseded"로 밀어내고 그 늦은 답은 버린다. 실패(워커 시작 실패 포함)는 오류 줄과 "다시 분석"으로 알린다.
- **분석 대상은 원본 이미지**다(편집한 결과가 아니다). 추출이 항상 원본에서 자르는 것과 같은 규칙이라, 레이어를 옮기거나 잠그거나 숨겨도 후보는 같다. 분석은 도구를 처음 켤 때 한 번 하고(새 이미지·프로젝트를 열면 버리고 다시 한다), 프로젝트 파일·임시저장에는 들어가지 않는다.
- **도구**: 자동 후보(A). 켜면 후보 상자가 **주황 점선**(4px 선, 3px 틈)으로 보이고(작은 것은 화면에서 4px 미만이면 그리지 않고, 너무 많으면 큰 것 1500개까지만 그린다), 포인터 아래 가장 작은 후보는 연하게 칠해진다. **클릭하면 그 자리의 가장 작은 후보가 선택**되고, **같은 자리(4px 이내)를 다시 클릭할 때마다 한 단계 큰 후보**로 바깥으로 나가며, 가장 큰 것 다음에는 다시 가장 작은 것이다. 다른 자리를 클릭하면 그 자리의 가장 작은 것부터 다시 시작한다. 후보가 없는 자리를 클릭하면 선택이 풀린다. 선택하면 아래쪽 표시줄에 "n/m · 너비 × 높이 px"와 **추출(Enter)**, **해제(Esc)**가 나온다.
- **추출은 기존 수동 경로 그대로**다. `extractCandidatePick` → `beginExtraction(후보 상자)`: 배경색 샘플링, 모호하면 색 질문(그때는 레이어가 아직 없다), 레이어+패치 Undo 1단계, 추출 뒤 선택 도구. 후보로 만든 레이어는 같은 상자를 손으로 끌어 만든 것과 **크롭·패치 색·픽셀·위치가 모두 같다**(E2E). 클릭 좌표는 이미지 픽셀로 바꿔서 쓰므로 확대 100%·200%, DPR 1·2에서 같은 후보가 나온다(E2E).
- **편집 막기**: 비교 보기에서는 점선도 표시줄도 없고 선택·추출을 스토어가 거부한다(거부되면 선택은 남는다). 도구를 벗어나면 선택과 하이라이트가 사라진다. 잠금·숨김 레이어는 후보와 무관하다(원본에서 분석하므로). Enter/Esc는 선택이 있을 때만 쓰고, 없으면 그대로 둔다.
- **너무 복잡한 화면**: 색이 계속 바뀌는 화면(사진·잡음)은 한 색 구간이 픽셀마다 생겨 메모리를 많이 쓴다. 3백만 픽셀 잡음에서 힙이 약 100MB(선형으로 늘면 12백만 픽셀에서 400MB, 33백만 픽셀에서 1GB 이상)라서, **구간 수가 600만을 넘으면 중단**하고 "색이 계속 바뀌는 복잡한 화면이라 후보를 찾지 못했습니다. 수동 영역 추출은 그대로 쓸 수 있습니다."를 보인다(E2E: 3200×2000 잡음).
- **정확도(측정)**: `tests/fixtures/realistic-capture.png`(960×600, 알려진 요소 10개)를 도구로 클릭해서 쟀다. 각 요소의 중심을 클릭하고, 선택된 상자와 정답의 IoU를 본다.

  | 요소 | 첫 클릭 IoU | IoU 0.85 이상에 이르는 클릭 수 | 최고 IoU |
  |---|---|---|---|
  | header | 1.000 | 1 | 1.000 |
  | card0 / card1 / card2 | 1.000 | 1 | 1.000 |
  | thumb0 (그림) | 1.000 | 1 | 1.000 |
  | textbar0 (글자 막대) | 1.000 | 1 | 1.000 |
  | button0 / button1 / button2 | 0.150 | 2 | 1.000 |
  | wide (넓은 카드) | 0.018 | 2 | 1.000 |

  모든 요소에 최대 2번 클릭으로 닿았다. 첫 클릭이 버튼·넓은 카드에서 낮은 것은 **"가장 작은 후보부터"라는 설계 때문**이다(버튼 안의 글자 영역, 넓은 카드 안의 첫 요소가 먼저 잡힌다). 합성 캡처(400×300, 카드 2·버튼·글자 막대)는 단위 테스트가 IoU 0.98 이상으로 모두 찾고 점 3개는 찾지 않음을 확인한다(`candidates.test.ts`가 표를 출력). 같은 그림을 워커가 분석한 결과는 이 스레드에서 분석한 결과와 **완전히 같다**(E2E).
- **측정(속도)**: 워커 분석 4000×3000(카드 50개, 후보 150개) 112ms, 도구를 켠 뒤 점선이 보일 때까지 297ms, 그 사이 페이지는 16프레임을 그렸고 가장 긴 틈이 51ms였다(100ms 넘는 틈 0). 8192×4096(카드 147개, 후보 441개) 247ms / 481ms / 틈 최대 73ms(0회). 헤드리스 Chromium 한 대, 한 번씩. 단순한 캡처 기준이며 복잡한 화면은 위 한계가 있다.
- **알려진 한계**: (1) 헤더가 있는 캡처에서는 헤더 아래 배경 전체(프레임의 89%)가 후보 하나로 잡힌다. 90% 임계값을 넘지 않아서이며 임계값은 바꾸지 않았다(넓은 본문 영역을 못 찾게 될 수 있어서). 빈 배경을 클릭하면 이 큰 영역이 선택된다. (2) 사진·그라데이션이 큰 이미지·반투명 겹침은 잘 못 찾는다(텍스처는 후보가 되지 않음). (3) 둥근 모서리·원형 요소는 바깥 사각형으로만 잡는다. (4) 테두리가 있는 카드는 안쪽 면과 테두리가 따로 후보일 수 있다. (5) 텍스트를 줄 단위로 묶거나 아이콘을 하나로 합치지는 않는다. (6) 허용치 4는 이 두 캡처로 정한 값이라 다른 캡처에서는 맞지 않을 수 있다(조절 UI 없음).

## 6. 키보드 레이어 이동 (결정)

- 선택한 레이어를 방향키로 **1px**, Shift+방향키로 **10px** 옮긴다. 단위는 항상 **원본 이미지 픽셀**이라 확대율·화면 배율과 무관하다(200%에서도 1px).
- **Undo 정책(애매해서 정한 것)**: 같은 레이어에 대한 키 입력이 **600ms 안에 이어지면 한 단계**로 합친다(키를 누르고 있어도 한 단계). 600ms 넘게 쉬거나, 그 사이에 다른 편집이 끼면 새 단계다. 합칠 때는 직전 단계를 되돌리고 합계로 한 번 다시 기록한다(히스토리에는 좌표 차이만 남는다). 합계가 0이면 단계를 남기지 않는다.
- **막는 경우**: 입력창에 포커스가 있을 때, 대화상자(내보내기·복원·색 질문)가 열려 있을 때, 선택된 레이어가 없을 때(방향키는 원래 동작), 잠긴 레이어, 원본/수정본 비교 중. 잠금·비교는 스토어(`nudgeLayer`)가 강제한다. Ctrl·⌘·Alt와 함께 누른 방향키는 브라우저 몫이다.
- 숨김 레이어도 선택돼 있으면 움직인다(숨김은 이동 금지가 아니다).
- 프레임 밖으로 나가는 이동은 막지 않는다(마우스 이동과 같은 규칙).
- **측정**(Node, 4000×3000 캡처, 3000×2000 레이어): 키 200번에 21.7ms, 한 번에 0.11ms. 픽셀을 건드리지 않고 `transform`만 바꾼다.

## 7. 다중 선택·그룹 이동, 정렬 가이드·스냅 (결정)

설계는 구현 전에 `CLAUDE.md`에 먼저 적고 커밋했다(`6875142`). 구현은 그 설계대로이며 아래는 구현에서 정한 세부와 측정이다.

- **선택**: Shift 또는 Ctrl/⌘ + 클릭이 선택에 더하거나 뺀다(캔버스·레이어 패널 모두). **Ctrl+A**는 모든 레이어를 선택한다(입력창에 포커스가 있으면 그 입력창의 전체 선택). 일반 클릭은 하나만 고르고, 여러 개가 선택된 상태에서 그 멤버를 (끌지 않고) 클릭하면 그 레이어 하나로 좁혀진다. 선택에서 빠진 레이어는 Shift를 누른 채 끌어도 움직이지 않는다. 숨김 레이어는 캔버스에서 선택되지 않는다(패널에서는 가능, 기존 규칙). 선택은 UI 상태라서 저장·임시저장에 들어가지 않고, 기록(Undo)에도 남지 않는다.
- **그룹 이동**: 선택된 레이어 하나를 끌면 선택된 잠기지 않은 레이어 전부가 같은 거리만큼 움직이고 **놓을 때 Undo 1단계**(좌표만 기록). 끄는 동안 다른 레이어들은 같은 거리로 따라 움직이는 것이 보이며 저장은 놓을 때뿐이다. 선택에 없는 레이어를 끌면 그 레이어만 움직이고 선택이 그것 하나가 된다. 방향키(1px, Shift는 10px)는 선택 전체를 움직이고, **같은 레이어 집합**에 대한 600ms 이내 입력은 한 단계로 합친다(집합이 다르면 새 단계, 순서는 무관). 잠긴 레이어는 선택은 되지만 제자리에 남고, 모두 잠겼으면 움직이지 않는다. 비교 보기에서는 드래그·방향키·삭제를 스토어가 거부한다.
- **여러 개 선택했을 때 안 되는 것**: 크기 조절·회전(핸들 없음), 이름·속성 패널(대신 "N개 선택됨 · 이동·삭제만 가능"), 복제·복사(Ctrl+D/C는 안내 줄을 보이고 아무것도 안 함), 앞/뒤 순서. 삭제는 선택된 것 중 잠기지 않은 전부를 **1단계**로 지우고 잠긴 것은 남기며 "잠긴 레이어 N개는 삭제되지 않았습니다"를 알린다(전부 잠겼으면 아무것도 안 함).
- **스냅**: 움직이는 상자(선택 전체의 바깥 상자, 회전한 레이어는 회전한 뒤의 바깥 상자)의 왼쪽·가운데·오른쪽, 위·가운데·아래가 **보이는** 다른 레이어와 프레임의 같은 선에 화면 6px(÷ 확대율 = 이미지 px) 이내면 붙는다. x·y는 따로, 거리가 가장 작은 후보가 이기고 같으면 먼저 찾은 것이다. 선택된 레이어끼리, 숨김 레이어와는 붙지 않는다. 그룹은 **하나의 상자로** 붙는다(끄는 레이어가 아니라 그룹의 바깥 가장자리가 선에 닿는다: E2E에서 끌지 않는 레이어가 그룹의 맨 왼쪽일 때로 확인). **8px 간격**: 이웃 상자와 정확히 8px(오른쪽 = 이웃 오른쪽+8, 왼쪽 = 이웃 왼쪽−8, 위아래도 같게) 떨어지도록 붙고, 반대 축에서 두 상자의 구간이 겹치거나 8px 이내일 때만 후보가 된다. 맞닿는(간격 0) 정렬도 정렬 후보이므로 8px 후보와 같은 거리면 먼저 찾은 쪽(정렬)이 이긴다. 가이드는 붙은 선마다 분홍(#ff3d81) 1px 선분으로 그려지고 8px 간격에는 "8"이 붙으며, 놓거나 취소하면 사라진다. **Alt를 누르고 있는 동안** 또는 캔버스 오른쪽 위의 **"스냅" 스위치**가 꺼져 있으면 붙지 않는다(기본 켬, 스위치는 프로젝트를 새로 열어도 유지). 위치는 항상 정수라 회전해서 바깥 상자의 가장자리가 정수가 아니면 붙은 선이 최대 0.5px 어긋날 수 있다.
- **계산은 순수 함수**: `snapMove`(`src/features/snap/snap.ts`)와 `layerBox`(`layer-box.ts`: 비트맵·벡터·회전·크기 조절을 반영한 바깥 상자). 단위 테스트 20개 + 선택·그룹 이동·삭제·키보드 28개.
- **측정**(헤드리스 Chromium, 100개 레이어, 한 번씩): 전체 선택 0.1ms, 그룹 이동(놓을 때) 2.4ms, 그룹 방향키 1.3ms, Undo 1.5ms, 전체 삭제 1.6ms. 레이어 100개를 모두 선택해 끄는 동안(스냅 켬) 53프레임, 평균 프레임 간격 23ms, 가장 긴 간격 94ms(소프트웨어 렌더링이라 실제 GPU에서는 더 나을 수 있다).
- **알려진 한계**: 드래그 사각형(마퀴)으로 선택하는 기능, 그룹 만들기, 여러 레이어 한꺼번에 크기·회전은 없다. 스냅은 드래그에만 있다(방향키·크기 조절·회전·브러시에는 없다). 간격 값(8px)과 임계값(6px)은 설정할 수 없다. 레이어가 아주 많으면(수백 개) 끄는 동안 후보 계산이 O(n)이라 느려질 수 있으나 100개에서는 문제가 없었다. 여러 개를 선택한 상태에서 한 레이어를 메모·텍스트 편집하는 등의 조합은 별도로 확인하지 않았다.

## 막힌 것

없다. 일곱 기능 모두 구현했다. 다만 아래는 **확인하지 못했거나 알려진 한계**이며 기능별 절에도 있다.

- 헤드리스 Chromium 한 대에서만 확인했다. 다른 브라우저, 실제 GPU, 터치, 장시간 사용, 한글 IME 조합 중의 포커스 이동(텍스트·메모 입력)은 확인하지 못했다.
- 텍스트 줄바꿈은 사용자 컴퓨터의 글꼴에 따라 달라진다(프로젝트는 글꼴을 담지 않는다). 같은 컴퓨터에서 화면과 PNG는 같다.
- 자동 영역 후보: 헤더가 있는 캡처에서 헤더 아래 배경 전체(프레임의 89%)가 후보 하나로 잡힌다(임계값 90%, 바꾸지 않음). 사진·텍스처는 찾지 못하고, 구간이 600만 개를 넘는 복잡한 화면은 중단한다.
- 스냅이 **기본 켬**이라서 드래그의 위치가 가까운 선(6px 이내)으로 끌려간다. 정확한 픽셀 위치가 필요하면 Alt를 누르거나 "스냅" 스위치를 끈다. 이 때문에 기존 E2E 두 개를 고쳤다(정확한 거리를 재는 복제 이동 테스트는 스냅을 끄고, 성능 측정의 원형 드래그는 끝점이 출발점과 같을 때 스냅이 원위치로 되돌리는 것을 허용).
- 전체 E2E를 한 번에 돌리다 시스템 메모리 부족으로 두 번 중단됐다. 그 뒤로는 spec 파일 하나씩 돌렸다. 그때 `brush.spec.ts`가 개발 모드에서 1건, 프로덕션에서 1건(다른 시점) 일회성으로 실패했고 단독 재실행에서는 모두 통과했다. **원인은 확인하지 못했다.**
